# 询盘页与 EBMS 对接

## 背景

现有思路是保留一个带高级交互的 `inquiry.html`，让客户提交询盘后进入 EBMS，供业务员跟进、报价和转订单。对话中出现的 Gitee 地址是内部仓库线索，当前没有读取源码，因此下面的技术栈和接口均不能视为已确认事实。

## 推荐架构

### 方案 A：静态页面提交 EBMS API（首选）

```text
客户填写 inquiry.html
        ↓
前端校验 + 提交中/成功/失败反馈
        ↓
EBMS /api/inquiry
        ↓
询盘表 → 业务员跟进 → 报价 → 订单
```

适合先快速跑通链路。需要 EBMS 提供接收接口、鉴权、CORS 和数据落库能力。

### 方案 B：中间表再同步

官网先写入独立 `inquiries` 表，EBMS 通过定时任务或 Webhook 同步。适合暂时不能修改 EBMS 的情况，但必须设计去重、重试和导入状态。

### 方案 C：直接并入 EBMS 模块

把询盘页做成 EBMS 的路由和权限模块，后期最规整，但前期改造面最大。

## 最小数据模型

建议至少记录：

- 客户姓名、邮箱、国家/地区。
- 产品关键词、数量、留言。
- 来源页面、来源渠道、提交时间。
- 状态：`new`、`contacted`、`quoted`、`closed`。
- 业务员备注、最近跟进时间。

## 前端交互要求

- 必填项和邮箱格式即时校验。
- 提交按钮具有默认、加载、成功、失败四种可识别状态。
- 成功后显示预计响应时间和回退联系方式。
- 失败时保留用户输入，并提供邮件或 WhatsApp 等备用渠道。
- 不在前端写入数据库密码、API Key 或内部服务凭据。

## 开始开发前必须确认

1. EBMS 的后端语言和框架。
2. 实际 API 基础地址、端口和鉴权方式。
3. 数据库类型与询盘表是否已经存在。
4. `inquiry.html` 的部署地址，以及是否跨域。
5. 是否需要邮件确认、垃圾提交防护和附件上传。

## 联调清单

- 正常提交：页面成功态、数据库新增记录、后台可见。
- 参数校验：缺少必填项和错误邮箱被拒绝。
- 服务异常：API 关闭时页面给出可理解的失败提示。
- 重复提交：按钮锁定或后端幂等，避免重复询盘。
- 安全性：HTTPS、CORS 白名单、速率限制、输入清洗和日志脱敏。

## 重要备注

对话里给出的 Node/Express、PHP、MySQL 和内网端口均是示例，不是当前 EBMS 的确认配置；实施前必须以仓库、部署文件和实际环境为准。
